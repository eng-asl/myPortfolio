How FTP Works

FTP (File Transfer Protocol) is an application-layer protocol in the TCP/IP stack (alongside HTTP and POP) used to transfer files between a client and a server over TCP.

Unlike single-connection protocols, FTP separates commands and file transfers across two distinct TCP connections.

ChannelPurposePort
Control ChannelCommands and server responses.TCP 21 by default.
Data ChannelFiles and directory listings.TCP 20 as the traditional Active mode source port (depending on configuration), or a negotiated server port in Passive mode.

Control Channel

The Control Channel exchanges FTP commands and server responses. It normally remains open throughout the FTP session.

Data Channel

The Data Channel transfers files and directory listings. It is normally opened when a transfer is required and closed when that transfer finishes.

Active and Passive FTP

FTP supports two modes for establishing the Data Connection. In both modes, the client initiates the Control Connection.

ModeConnection initiator
Active FTPServer
Passive FTPClient

Active FTP

The client uses the PORT command to tell the server which client endpoint to connect to. The server initiates the Data Connection back to that endpoint.

Passive FTP

The client uses the PASV command to request a server listening endpoint. The client then initiates the Data Connection outbound.

vsFTPd

vsFTPd (Very Secure FTP Daemon) is a commonly used Linux FTP server. FTP defines the communication protocol, while vsFTPd implements it on the host.

A daemon is a program that provides a background service. The default configuration file is /etc/vsftpd.conf.

vsFTPd Configuration Settings

Directives in /etc/vsftpd.conf govern network listeners, authentication, filesystem isolation, listings, banners, logging, and TLS.

Network and Connection Settings

SettingDescription
listen=NOControls standalone IPv4 operation. When YES, vsFTPd listens independently. When both listen and listen_ipv6 are NO, a superserver such as inetd can start vsFTPd when a connection is requested.
listen_ipv6=YESEnables independent listening on an IPv6 socket, which may also accept IPv4 connections depending on system configuration.
connect_from_port_20=YESConfigures vsFTPd to use server TCP port 20 as the source port for Active FTP Data Connections.

On-demand operation saves memory when FTP is rarely used. It does not hide the FTP service from port scanning because another service such as inetd still listens on port 21.

Authentication and Access Control

SettingDescription
anonymous_enable=NODisables anonymous login.
local_enable=YESAllows existing Linux system accounts to authenticate to FTP.
pam_service_name=vsftpdSelects the PAM authentication configuration, normally at /etc/pam.d/vsftpd. PAM is also used by SSH and sudo.
secure_chroot_dir=/var/run/vsftpd/emptyDefines an empty, restricted directory used to isolate pre-authentication vsFTPd processes from system files.

Before authentication, the process handling incoming FTP commands does not require direct access to sensitive system files. vsFTPd isolates this process inside secure_chroot_dir under the Principle of Least Privilege; this is not the directory used for sharing, uploading, or downloading files.

Ownership and User Restrictions

SettingDescription
chown_uploads=YESChanges the ownership of anonymously uploaded files.
chown_username=usernameSpecifies the Linux account receiving ownership.
chroot_local_user=YESRestricts local FTP users to their configured root directory.
chroot_list_enable=YESEnables /etc/vsftpd.chroot_list, whose behavior depends on chroot_local_user.

Authenticated user confinement applies to /etc/vsftpd.chroot_list, which is distinct from pre-login secure_chroot_dir isolation.

Information Disclosure and Directory Listing

SettingDescription
hide_ids=YESDisplays file owners and groups as ftp instead of real UIDs or usernames.
ls_recurse_enable=YESEnables recursive directory listings using LIST -R.

Enabling hide_ids alters displayed ownership fields in FTP protocol listings without changing actual file ownership or Linux permissions.

Messages, Time and Logging

message_file=.messageDefines the file containing the directory entry notice.

xferlog_enable=YESLogs file uploads and downloads for auditing.

Encryption and Security

SettingDescription
ssl_enable=NODisables TLS support. Set to YES to allow FTPS connections.
rsa_cert_filePath to the server X.509 TLS certificate.
rsa_private_key_filePath to the private key paired with the certificate.

Standard FTP transfers credentials and file contents in plain text. Enabling TLS support (ssl_enable=YES) and enforcing encrypted logins or data transfers are separate configuration concerns.

ProtocolSecurity
FTPPlain text.
FTPSFTP with TLS encryption.
SFTPFile transfers over SSH using a separate protocol.

FTP Users and Access Control

The /etc/ftpusers file lists usernames that are denied FTP access when the authentication policy enforces this denylist.

Inspect /etc/ftpusers
$cat /etc/ftpusers

Enforcing this list helps prevent sensitive or privileged Linux accounts from authenticating over FTP unnecessarily.

Dangerous Settings and Anonymous Access

Anonymous FTP permits access without a personal user account. It can support internal distribution, yet permissive settings risk exposing files or allowing unauthorized writes.

SettingDescription
anonymous_enable=YESAllows anonymous login.
no_anon_password=YESRemoves the anonymous password prompt.
anon_root=/home/username/ftpSets the directory exposed as root to anonymous users.
write_enable=YESEnables filesystem-modifying FTP commands.
anon_upload_enable=YESAllows anonymous uploads when required permissions permit.
anon_mkdir_write_enable=YESAllows anonymous directory creation when permitted.

Anonymous access risks include unauthorized reads, filename disclosure, and unintended file uploads or disk consumption; anonymous writes require both write_enable=YES and matching Linux filesystem write permissions.

Debugging FTP Communication

FTP clients provide diagnostic commands to inspect local client settings and raw protocol exchanges.

CommandPurpose

When ls_recurse_enable=YES is active on the server, the client can enumerate accessible subdirectories recursively.

Recursive directory listing

Downloading and Uploading Files

Security Implications

Writable FTP directories become critical when shared with downstream services such as web application roots. Upload permission alone does not grant code execution; additional vulnerabilities, loose permissions, or insecure integrations are required.

Footprinting FTP with Nmap

Nmap detects FTP services, versions, and configuration exposure using the Nmap Scripting Engine (NSE).

FTP Scripts

NSE scripts are commonly stored under /usr/share/nmap/scripts/. Running --script-updatedb rebuilds Nmap's local script database index rather than downloading new scripts.

Rebuild script index and locate FTP scripts
$sudo nmap --script-updatedb
$find / -type f -name "ftp*" 2>/dev/null | grep scripts

Service Enumeration

Run a focused FTP version and default-script scan:

Focused FTP scan
$sudo nmap -sV -sC -p21 10.129.14.136
OptionPurpose
-sVService and version detection.
-sCDefault NSE script scanning.
-p21Scans TCP port 21.

Output can reveal anonymous access, server software versions, accessible directories, and session parameters.

Nmap Script Trace

Adding --script-trace logs network exchanges sent and received by NSE scripts.

Trace NSE packet exchanges
$sudo nmap -sV -sC -p21 10.129.14.136 --script-trace

Manual FTP Interaction and TLS

Netcat and Telnet probe banners and raw commands on TCP port 21, while OpenSSL inspects FTPS certificates over STARTTLS.

Manual Interaction

Netcat and Telnet open raw control connections on port 21 for manual commands, though they do not automatically manage separate FTP Data Connections.

Connect with Netcat or Telnet
$nc -nv 10.129.14.136 21
$telnet 10.129.14.136 21

FTP over TLS

OpenSSL upgrades a plain-text FTP control socket via -starttls ftp to inspect TLS parameters and X.509 certificates. Certificate Subject fields may reveal hostnames or organization names, but should not be trusted as verified identity, especially for self-signed certificates.

Inspect FTPS certificate with OpenSSL
$openssl s_client -connect 10.129.14.136:21 -starttls ftp

Inspect Control Channel

Persistent TCP control session (default port 21) used to negotiate authentication, data modes, file commands, and status responses.

  • TCP connection establishment: Client initiates a three-way handshake to server TCP port 21 before any FTP commands are sent.
  • Client and server communication: Both ends send ASCII protocol commands and numeric replies bidirectionally over this control stream.
  • USER and PASS authentication: Credentials (or anonymous login) are submitted on the control socket unless TLS via AUTH TLS protects the stream.
  • PORT and PASV negotiation: Coordinates which IP and TCP port will carry the next Data Channel transfer.
  • LIST, RETR, and STOR commands: Trigger directory listings, file downloads, and file uploads.
  • Three-digit response codes: Server status codes such as 220, 230, 200, 150, 226, and 530 synchronize every step.
  • Session lifecycle and termination: Stays open across multiple transfers until the client sends QUIT (221 Goodbye) or the server idle timeout expires.

Inspect Data Channel

On-demand TCP connection dedicated to transferring directory listings and file payloads cleanly alongside the Control Channel.

  • Temporary TCP connections: Opened for a single LIST, RETR, or STOR transfer and closed cleanly once complete.
  • Uploading and downloading: Carries file bytes from client to server on STOR and from server to client on RETR.
  • Directory listings: Returns folder entries and permissions on LIST or LIST -R rather than mixing raw file listings into control replies.
  • Transfer lifecycle and Control relationship: Negotiated on the Control Channel first (200 after PORT/PASV, 150 before opening, 226 upon closing).
  • Port negotiation: Uses client-advertised ports in Active mode or server-advertised ephemeral ports in Passive mode.
  • Transfer restart markers: Interrupted transfers can resume when both client and server support restart markers (REST).
  • Initiation vs transfer direction: Whichever host initiates the TCP socket (server in Active mode, client in Passive mode) does not restrict which direction file bytes flow afterward.

Explore Active FTP

Mode in which the client advertises a listening endpoint with PORT and the server initiates the Data Connection back.

  1. Client port 51000 connects to server port 21 to open the Control Connection.
  2. Client sends PORT on the control channel to advertise its listening data endpoint, for example port 51001.
  3. Server initiates the Data Connection toward client port 51001, traditionally from source port 20 when configured (such as connect_from_port_20=YES).
  4. File data or directory listings then travel in the required direction.

Security note: Client-side firewalls and NAT routers commonly block incoming TCP connections initiated by the remote server toward client port 51001.

Explore Passive FTP

Mode in which the server opens a listening port after PASV so the client initiates both Control and Data Connections outbound.

  1. Client port 51000 connects to server port 21 to open the Control Connection.
  2. Client sends PASV over the control channel.
  3. Server replies with an ephemeral listening data port, for example port 52000.
  4. Client connects outbound from a local ephemeral port (for example 51002) to server port 52000.

Security note: Passive FTP generally traverses client-side firewalls and NAT more reliably because all connections originate outbound from the client, though the server must allow inbound traffic to its configured passive data port range.

vsFTPd Setup Guide

Install the vsFTPd package, filter active directives from /etc/vsftpd.conf, and consult the manual for omitted defaults.

  • Package installation runs on Debian or Ubuntu via apt and places default configuration in /etc/vsftpd.conf.
  • Note on filtering: grep -v "#" excludes every line containing a hash character (#) anywhere on the line, including settings followed by an inline # comment, rather than only full-line comments.
  • /etc/vsftpd.conf omits many supported options; run man vsftpd.conf to inspect every directive and default behavior.
$ sudo apt install vsftpd
$ cat /etc/vsftpd.conf | grep -v "#"
$ man vsftpd.conf

Service Startup & On-Demand Operation

Standalone listening vs superserver activation (listen, listen_ipv6, and connect_from_port_20).

  • Standalone IPv4 (listen=YES): vsFTPd remains running in the background listening on IPv4 TCP port 21.
  • On-demand mode (both listen=NO and listen_ipv6=NO): Another service such as inetd holds TCP port 21 and launches vsFTPd only when needed, saving RAM when FTP is rarely used.
  • Default Linux distributions often set listen=NO alongside listen_ipv6=YES so one dual-stack IPv6 socket handles connections independently.
  • Active FTP source port (connect_from_port_20=YES): Requests outgoing Active Data Connections originate from port 20, though Active data port behavior remains configuration-dependent.

Security note: On-demand startup does not conceal FTP from Nmap or port scanners because inetd or systemd still keeps TCP port 21 open and listening.

Pre-Auth Process Isolation (secure_chroot_dir)

Confines unprivileged pre-authentication vsFTPd command handlers inside empty directory /var/run/vsftpd/empty.

  • Principle of Least Privilege: Pre-login command handlers parse network input without needing visibility into /etc, /home, or /var.
  • Distinct purpose: secure_chroot_dir=/var/run/vsftpd/empty is reserved exclusively for daemon isolation and is never used for user file sharing, uploads, or downloads.

Security note: Chroot limits filesystem traversal to a restricted directory tree; it is not a complete security boundary that prevents every possible form of process or kernel compromise.

Authenticated User Chroot Rules

Controls whether authenticated local Linux accounts can browse outside their home directories via chroot_local_user and /etc/vsftpd.chroot_list.

  • Process isolation vs user restriction: secure_chroot_dir isolates pre-auth vsFTPd workers inside an empty directory, whereas chroot_local_user restricts authenticated local logins after authentication.
  • Enabling write permissions on a chrooted home directory interacts with vsFTPd writeable-chroot protections (allow_writeable_chroot).

Behavior when chroot_list_enable=YES (/etc/vsftpd.chroot_list)

chroot_local_userUsers in the enabled chroot list
YESExceptions to the restriction (can browse outside their home).
NOUsers who are restricted (everyone else remains unrestricted).

Security note: Accidental reversal of YES/NO leaves system directories readable to FTP logins. As with all chroot configurations, treat chroot as defense-in-depth filesystem restriction rather than an absolute sandbox.

Compare Directory Listings (hide_ids & Fail2ban)

Illustrative example

Contrasts raw UID/username disclosure in FTP listings against masked ftp/ftp ownership with hide_ids=YES.

  • hide_ids=YES rewrites displayed owner and group strings to ftp in protocol LIST output without changing real Linux UID/GID ownership or on-disk permissions.
  • Exposed usernames (or UID numbers tied to shared host accounts) help attackers assemble valid username lists for brute-force or credential-stuffing attacks against FTP or SSH.
  • Defensive layer: Properly configured Fail2ban monitors authentication logs (such as vsFTPd or SSH failures) and bans offending client IPs after repeated failed login attempts.
-rw-rw-r-- 1 1002 1002 Calendar.pptx   # Default listing exposes UID/owner
-rw-rw-r-- 1 ftp  ftp  Calendar.pptx   # With hide_ids=YES enabled

Transport Security: FTP, FTPS, and SFTP

Separates cleartext FTP from TLS-encrypted FTPS (rsa_cert_file, rsa_private_key_file, ssl_enable) and SSH-based SFTP.

  • Default Debian/Ubuntu certificate paths commonly point to /etc/ssl/certs/ssl-cert-snakeoil.pem (rsa_cert_file) and /etc/ssl/private/ssl-cert-snakeoil.key (rsa_private_key_file).
  • Enabling TLS vs enforcing TLS: Setting ssl_enable=YES enables FTPS capability on vsFTPd, whereas enforcing encryption for all sessions requires additional directives such as force_local_logins_ssl and force_local_data_ssl.
  • FTP and SFTP are separate protocols: FTPS wraps RFC 959 FTP over TLS inside vsFTPd, while SFTP is the SSH File Transfer Protocol subsystem running over SSH.

Security note: Standard plain-text FTP exposes usernames, passwords, commands, and file payloads to passive packet capture on shared networks.

PAM Authentication and /etc/ftpusers Denylist

Illustrative example

How /etc/pam.d/vsftpd enforces the /etc/ftpusers denylist to block privileged or designated accounts.

  • When PAM rules in /etc/pam.d/vsftpd invoke pam_listfile.so (pointing to /etc/ftpusers), listed accounts receive 530 Login incorrect even with valid OS passwords.
  • Administrators add root, service accounts, or restricted local usernames to reduce attack surface.

Anonymous Access Risk Scenarios

Operational and security consequences of permissive anonymous_enable, no_anon_password, anon_root, and write flags.

  • Information disclosure: Public directory trees and leftover backup or template files under anon_root reveal internal projects, client names, or credentials.
  • Unauthorized uploads: write_enable=YES plus anon_upload_enable=YES (with writable Linux permissions) allows external clients to upload malware, Phishing assets, or unwanted payloads.
  • Unauthorized file modification or deletion: Existing files in shared upload paths can be overwritten or removed via STOR and DELE.
  • Storage abuse: Repeated uploads or directory creation via anon_mkdir_write_enable=YES can exhaust server disk quotas and disrupt local services.

Security note: Keep anon_root non-writable for anonymous FTP accounts unless an isolated, non-executable dropbox is explicitly required.

Conditional Security Implications of Writable FTP

How writable FTP folders intersect with downstream services, and the preconditions required for severe impact.

  • Unauthorized file modification: Replacing static templates, scripts, or shared documents.
  • Information exposure: Writing configuration traps or reading shared internal resources.
  • Local File Inclusion (LFI): If a vulnerable web application includes files located inside the writable FTP folder.
  • FTP log poisoning: If server transfer or error logs containing user-controlled filenames/strings are parsed unsafely or included by a web script.
  • Remote Code Execution (RCE) and privilege escalation: Conditional outcomes when an executable script lands inside a web root, cron job, or privileged import path.

Security note: Important qualification: FTP upload access alone does not execute files. Code execution occurs only when chained with secondary weaknesses, excessive OS permissions, or insecure web/application integrations.
